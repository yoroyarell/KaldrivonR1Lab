SON to rApp Migration Workbench

Trace a SON function from its original contract through R1 services to an observed outcome.

Public AT&T and Ericsson material on moving SON functionality toward a Non-RT RIC and rApp environment motivates this topic. All cells, numbers, rules, approvals and outcomes in this application are fictional. Nothing here controls a live RAN.

Migration path at a glanceHow a SON function works once it moves into an rApp. Read left to right: the contract feeds the rApp, the rApp only talks R1, and the platform reaches the network for it.
Legacy SON contract→ rApp→ R1 services→ SMO / Non-RT RIC→ O1 to managed RAN functions; A1 to Near-RT RIC where relevant→ Simulated RAN
Legacy SON contract
A written description of what today's SON function does: what starts it, what it reads, what it decides, what it may change and how success is judged. It is extracted first, before any code moves.
rApp
The new application that holds the decision logic. It runs on the SMO platform and never talks to network equipment directly.
R1 services
The rApp's only doorway: service discovery and access control, data subscriptions, network information, alarms, measurements, configuration and A1 policies. R1 is a family of services, not one API.
SMO / Non-RT RIC
The platform that hosts rApps, checks what each one is allowed to do, and carries approved requests to the network on its behalf.
O1 and A1
The platform's own links toward the network. O1 configures and monitors RAN functions; A1 sends policies to the Near-RT RIC. The rApp uses them only indirectly, through R1.
Simulated RAN
The fictional cells in this demo. Nothing here reaches a real network.
